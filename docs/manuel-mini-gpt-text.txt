Le fil conducteur
Un texte devient une suite d’entiers. Ces entiers désignent des vecteurs. L’attention combine les
informations accessibles dans le passé. Le réseau attribue des scores aux prochains tokens. Une
fonction de coût mesure l’erreur, puis la rétropropagation indique comment modifier ses paramètres.
Enfin, la génération répète la prédiction, un token après l’autre.

Un livre fondé sur une implémentation réelle
Ce manuel accompagne les sept scripts Python, le notebook pédagogique et les tests du dépôt
hackolite/SHOKOBO. Il distingue systématiquement les principes généraux des choix précis de cette
implémentation : tokenisation caractère ou BPE, blocs post-normalisés, positions apprises ou RoPE,
attention manuelle ou SDPA, et cache KV à fenêtre reconstruite.




Périmètre de lecture : code de référence ae314c6. Les exemples numériques du manuel sont didac-
tiques, sauf mention explicite d’une valeur calculée à partir du code. Aucun résultat d’entraînement
ni benchmark matériel n’est présenté comme une mesure effectuée.

Mode d’emploi et conventions
À qui s’adresse ce manuel ?
Vous savez manipuler une fonction, lire une somme, calculer une dérivée simple et utiliser les
probabilités du lycée. Vous n’avez pas besoin d’avoir étudié les matrices, les tenseurs, l’optimisation
ou les réseaux de neurones : les premières fiches construisent ces notions. Une connaissance élémentaire
de Python aide ; les objets du langage utiles au projet sont expliqués au fil du texte. Ce livre n’est
toutefois pas un cours exhaustif du langage Python.
Comment travailler une fiche
Lisez son objectif, refaites les calculs au crayon, puis retrouvez le symbole indiqué sous le titre dans
le fichier source. Cachez la correction avant de résoudre l’exercice. Les explications concernent le
code exécuté, qui fait foi lorsqu’un schéma introductif simplifie certains détails. Une fiche occupe
une page ; le sommaire donne à la fois son numéro et sa page physique.
Quatre parcours successifs
    1. Fiches 1–24 : construire les outils mathématiques et comprendre comment une probabilité
       devient une erreur à minimiser.
    2. Fiches 25–48 : suivre le texte jusqu’aux lots de fenêtres, sans contamination de la validation.
    3. Fiches 49–72 : parcourir les embeddings, l’attention, le Transformer et leurs variantes, en
       contrôlant chaque dimension.
    4. Fiches 73–96 : entraîner, évaluer, sauvegarder, générer et expérimenter sans confondre dé-
       monstration et performance industrielle.
Dictionnaire des dimensions

          Symbole    Signification
             B       Nombre de fenêtres dans un lot (batch)
             T       Longueur de la séquence actuellement traitée
             C       Longueur maximale du contexte
             V       Taille du vocabulaire (ne pas confondre avec les valeurs d’attention)
             D       Dimension des représentations (embedding)
             H       Nombre de têtes ; dk = D/H est leur dimension
             F       Dimension cachée du réseau feed-forward
             L       Nombre de blocs Transformer

Les indices commencent généralement à zéro, comme en Python. Le logarithme est naturel : les
pertes sont donc exprimées en nats. Une matrice de valeurs d’attention pourra être notée Vatt lorsque
le contexte ne suffit pas à la distinguer de la taille du vocabulaire.
Exécution et limites
Les chemins absolus correspondent au clone fourni ; adaptez leur racine sur votre ordinateur. Les
commandes d’expérimentation utilisent des sorties séparées sous /tmp pour ne pas écraser vos
checkpoints. Un modèle minuscule entraîné sur un petit texte n’est ni un assistant fiable ni une
source factuelle. L’exhaustivité recherchée est celle du pipeline de ce dépôt, pas celle de tout
l’apprentissage profond.

MiniGPT.forward

Objectif. Comprendre ce que calcule un modèle de langage avant d’étudier ses opérations.
Un texte arrive sous forme de caractères, non de nombres réels. Un tokeniseur le transforme en une
suite d’identifiants entiers. Dans le mode caractère du dépôt, un token représente généralement un
caractère ; dans le mode BPE, il peut représenter un fragment différent. Le vocabulaire est l’ensemble
des tokens disponibles et sa taille se note V . Un identifiant est une étiquette : le token numéro 8
n’est pas deux fois plus important que le token numéro 4.
La tâche est de prédire le token immédiatement suivant à partir des tokens déjà visibles. Pour une
suite fictive (2, 5, 1, 4), une fenêtre fournit l’entrée (2, 5, 1) et les cibles (5, 1, 4). À la première position,
le modèle doit proposer 5 en ne connaissant que 2 ; à la deuxième, il dispose du préfixe (2, 5). Le
mécanisme causal empêche de consulter les positions futures, même lorsqu’elles sont présentes dans
le tableau.
À comprendre. La chaîne de calcul.
Dans MiniGPT.forward, token_embedding transforme chaque identifiant en une liste de D nombres,
appelée représentation. Le mode positionnel appris ajoute position_embedding. Puis blocks,
final_norm et lm_head produisent des scores, les logits. Le mode RoPE traite autrement les
positions ; cela ne change pas l’objectif prédictif.

                 texte −→ identifiants −→ représentations −→ logits −→ probabilités.

Chaque position produit V scores, pas un identifiant directement. Une transformation appelée
softmax donnera des probabilités positives dont la somme vaut un. À l’entraînement, on mesure la
probabilité attribuée à la cible connue. En génération, on choisit un token, on l’ajoute à la suite,
puis on recommence. Ces deux usages partagent le même prédicteur.
Nous noterons B le nombre de fenêtres traitées ensemble, T leur longueur courante et C la capacité
maximale de contexte. Sans cache, on doit avoir 1 ≤ T ≤ C. Les L blocs transforment les représenta-
tions sans changer le nombre de positions. Aucun de ces nombres ne désigne une quantité de mots
comprise par la machine.
Exercice. Avec B = 2, T = 3 et V = 4, combien de scores et combien de cibles un passage produit-il ?
Quelle cible correspond au dernier token d’entrée de notre exemple ?
Correction détaillée. Chaque fenêtre fournit trois listes de quatre scores, donc 2 × 3 × 4 = 24
scores pour six cibles. La dernière entrée vaut 1, mais sa cible vaut 4 : recopier l’entrée ne résoudrait
pas la tâche. Les probabilités portent sur quatre possibilités à chacune des six positions, non sur les
six positions elles-mêmes.

Fiche 2 — Fonctions, arguments et indices Python
/home/runner/work/SHOKOBO/SHOKOBO/mini_gpt/02_dataset.py

NextTokenDataset

Objectif. Traduire les notations mathématiques en accès à une suite Python sans décalage accidentel.
Une fonction associe une sortie à une entrée autorisée. Au lycée, f (x) = 2x + 1 signifie qu’une même
recette s’applique à chaque valeur de x. Un programme peut recevoir une liste plutôt qu’un seul
nombre. SimpleTokenizer.encode, la méthode d’encodage du tokeniseur, reçoit un texte et renvoie
une liste d’entiers. Son domaine n’est donc pas celui d’une fonction polynomiale, mais l’idée d’une
transformation bien définie reste identique.
Une suite mathématique peut commencer à l’indice zéro : écrivons s0 , s1 , . . . , sN −1 pour N tokens.
Python adopte précisément cette convention. s[0] est le premier élément, tandis que s[N-1] est le
dernier. Les crochets indiquent un accès, pas une multiplication. Un indice compte les positions ; la
valeur rangée à cette position est une information distincte.
À comprendre. Les tranches excluent leur borne de droite.
L’expression s[a:b] prend les indices a, a + 1, . . . , b − 1. Si les bornes restent dans la liste et si b ≥ a,
elle contient b − a éléments. Dans NextTokenDataset, la longueur de fenêtre est context_length,
que nous notons C.
                              xt = si+t ,   yt = si+t+1 ,           0 ≤ t < C.
Pour s = (4, 7, 2, 9, 3), i = 1 et C = 3, l’entrée utilise les indices 1, 2, 3 : elle vaut (7, 2, 9). La cible
utilise les indices 2, 3, 4 : elle vaut (2, 9, 3). Les deux listes ont la même longueur, mais leurs contenus
sont décalés.
Lorsqu’on écrit une formule, annoncer le début des indices évite une ambiguïté fréquente : le «
troisième élément » est ici celui d’indice deux, pas celui d’indice trois.
Il faut un token supplémentaire pour connaître la dernière cible. Avec un pas de déplacement égal à
un, les débuts admissibles vont de zéro à N − C − 1, inclus : cela fait N − C fenêtres. Ne confondons
pas cette borne maximale avec le nombre de fenêtres. Le jeu de données sur disque ajoute un
paramètre de pas ; son comptage tient aussi compte de ce paramètre.
Enfin, logits[:, -1, :] emploie un indice négatif pour sélectionner la dernière position. Les deux
deux-points conservent les autres axes : ce n’est pas une sélection du dernier token du vocabulaire.
Exercice. Pour s = (8, 1, 6, 2, 5, 7), C = 2 et i = 2, donner s[i:i+C], la cible et le nombre total de
fenêtres.
Correction détaillée. L’entrée vaut (6, 2), la cible (2, 5). Les indices de début possibles sont 0, 1, 2, 3,
soit 6 − 2 = 4 fenêtres. Le début 4 serait impossible : sa deuxième cible demanderait l’élément
d’indice 6, absent de cette suite.

evaluate

Objectif. Lire le symbole somme et comprendre pourquoi une moyenne de moyennes peut tromper.
           P
Le signe , lettre grecque sigma, abrège une addition répétée. L’indice écrit en dessous parcourt les
valeurs indiquées ; chaque terme est calculé avant d’être ajouté. Par exemple, 3i=0 ai = a0 +a1 +a2 +a3 .
                                                                              P

Cet indice est local : remplacer partout i par j ne modifie pas le résultat. En revanche, changer les
bornes change les termes inclus.
La moyenne arithmétique de n > 0 valeurs partage leur somme en n parts égales. Pour les erreurs

Dans FeedForward.net, la première couche passe de D à F , une fonction GELU transforme les
valeurs, puis une seconde couche revient de F à D. Les mêmes paramètres s’appliquent à chaque
position de chaque exemple. La forme [B, T, D] devient donc [B, T, F ], puis [B, T, D].

développer a2 (a1 x + b1 ) + b2 donne (a2 a1 )x + (a2 b1 + b2 ). La fonction intermédiaire apporte donc
une capacité que la simple succession de sommes pondérées n’aurait pas.
Le biais agit indépendamment de l’entrée : si toutes les coordonnées reçues sont nulles, la sortie
est exactement le vecteur des biais. C’est une manière simple de vérifier son rôle et son orientation.
Une valeur de biais existe par sortie, pas par entrée ; elle est partagée entre les positions comme les
coefficients de la matrice.

Fiche 12 — Exponentielle et stabilité numérique
/home/runner/work/SHOKOBO/SHOKOBO/mini_gpt/03_attention.py

softmax_manual

Objectif. Comprendre pourquoi une formule exacte peut échouer avec des nombres flottants.
La fonction exponentielle, notée exp(x) = ex , associe un nombre strictement positif à tout réel fini x.
Elle vaut un en zéro, augmente avec x, et transforme les additions en multiplications : ea+b = ea eb .
Pour un nombre négatif, e−a = 1/ea . Ainsi une entrée négative ne produit jamais une exponentielle
négative.
Quelques repères suffisent : e ≈ 2,718, e2 ≈ 7,389 et e−2 ≈ 0,1353. Une différence additive de un
dans l’entrée multiplie la sortie par environ 2,718. Cette croissance rapide rend l’exponentielle utile
pour comparer des scores, mais délicate numériquement.
À comprendre. La machine n’utilise pas tous les réels.
Un format flottant dispose d’une précision et d’une plage finies. Une valeur trop grande peut devenir
+∞ : c’est un débordement. Une valeur positive trop petite peut être arrondie à zéro. En float32,
e1000 déborde largement, bien que ce nombre existe parfaitement en mathématiques.
La fonction softmax_manual, définie dans le script d’attention, commence par soustraire le maximum
de chaque ligne avant torch.exp. Pour les scores (1000, 999), elle exponentie donc (0, −1).

                                          e1000          1
                                                    =         ≈ 0,7311.
                                     e 1000 +e  999   1 + e−1
Le quotient initial pourrait devenir une opération indéfinie entre infinis dans le programme naïf.
Le quotient réécrit utilise des nombres modestes et donne la même valeur mathématique. Nous
démontrerons l’invariance générale du softmax plus loin.
Après soustraction d’un maximum fini, toutes les exponentielles sont au plus égales à un et au moins
l’une vaut exactement un. Leur somme ne peut donc pas s’annuler. Des termes très petits peuvent
encore être arrondis à zéro, mais ils ne font plus déborder le calcul des exponentielles.
La précision limitée affecte aussi les additions : ajouter une très petite quantité à une très grande
peut laisser le résultat inchangé après arrondi. Réécrire une formule n’est donc pas seulement une
question de présentation.
Point de vigilance. La stabilisation suppose une ligne contenant un score fini et aucun +∞. Si
tous les scores valent −∞, soustraire leur maximum produit des valeurs indéfinies. Masquer toutes
les possibilités n’est pas une distribution de probabilités valide.

Fiche 13 — Logarithme naturel : transformer les produits en sommes

Objectif. Donner un sens au logarithme d’une probabilité et à son opposé.
Le logarithme naturel ln est la fonction réciproque de l’exponentielle. Pour x > 0, ln(x) est l’unique
réel dont l’exponentielle vaut x. Ainsi ln(1) = 0, ln(e) = 1 et ln(e−2 ) = −2. Son domaine réel exclut
zéro et les nombres négatifs.
Cette fonction est croissante : une probabilité plus grande possède un logarithme plus grand. Pourtant,
entre zéro et un, le logarithme est négatif. Par exemple, ln(0,5) ≈ −0,6931 et ln(0,1) ≈ −2,3026. Le
signe négatif ne signale pas une erreur ; il est la conséquence normale d’une entrée inférieure à un.

                    ln(ab) = ln(a) + ln(b),       ln(a/b) = ln(a) − ln(b),    a, b > 0.

Ces identités se comprennent en écrivant a = eu , b = ev : leur produit vaut eu+v , donc son logarithme
vaut u + v. Attention, aucune identité analogue ne donne ln(a + b) = ln(a) + ln(b).
À comprendre. Mesurer la surprise d’une observation.
Pour une cible observée de probabilité p, la quantité − ln p est positive ou nulle. Elle vaut zéro si
p = 1 et augmente fortement quand p approche zéro. Cette mesure pénalise donc davantage une
cible jugée très improbable. Elle est exprimée en nats lorsqu’on utilise le logarithme naturel, plutôt
qu’en bits.
Dans MiniGPT.forward, F.cross_entropy calcule une perte liée à ce logarithme, directement à
partir des logits. Le code évite de demander explicitement le logarithme de probabilités déjà arrondies
à zéro. Les formules détaillées de cette perte apparaîtront après l’étude du softmax.
Pour une suite de prédictions, multiplier beaucoup de probabilités peut donner un nombre extrême-
ment petit. Dix probabilités égales à 0,1 donnent 10−10 ; leurs logarithmes s’additionnent et donnent
10 ln(0,1) ≈ −23,026. La représentation logarithmique garde ainsi une échelle plus maniable sans
modifier l’ordre de préférence entre probabilités positives.
Le logarithme mesure aussi des améliorations relatives. Passer d’une probabilité à une probabilité
deux fois plus grande diminue la surprise de ln 2, quelle que soit la valeur initiale, tant que la nouvelle
probabilité reste admissible. Ce comportement diffère d’une erreur mesurée par simple soustraction
des probabilités : le gain dépend d’un rapport, pas seulement d’un écart absolu.
Exercice. Deux cibles successives reçoivent les probabilités 1/2 et 1/4. Calculer le produit, son
logarithme et la somme des surprises.
Correction détaillée. Le produit vaut 1/8. Comme 8 = 23 , ln(1/8) = −3 ln 2 ≈ −2,0794. La somme
des surprises vaut ln 2 + ln 4 = 3 ln 2 ≈ 2,0794. On retrouve exactement l’opposé du logarithme du
produit : les contributions locales s’additionnent.

nécessaire qu’une personne annote chaque prochain caractère. Cette construction explique le terme

Fiche 20 — Dérivée : mesurer une variation locale
/home/runner/work/SHOKOBO/SHOKOBO/mini_gpt/06_train.py

train

Objectif. Retrouver l’idée de pente et comprendre ce que signifie un signal d’amélioration.
Pour une fonction réelle f , le quotient (f (a + h) − f (a))/h mesure la variation moyenne entre deux
entrées séparées par h ̸= 0. Si ce quotient tend vers une valeur finie lorsque h tend vers zéro, cette
limite est la dérivée f ′ (a). Elle représente la pente de la tangente au point d’abscisse a.

                                   f (a + h) − f (a)
                      f ′ (a) = lim                  ,        f (a + h) ≈ f (a) + hf ′ (a).
                               h→0         h
La deuxième relation est une approximation locale, pas une égalité pour n’importe quel déplacement.
Si f ′ (a) > 0, un petit déplacement positif augmente la fonction ; un petit déplacement négatif la
diminue. Une dérivée négative inverse ces indications.
À comprendre. Un calcul issu de la définition.
Pour f (x) = x2 , développer (a + h)2 donne a2 + 2ah + h2 . Le quotient de variation vaut donc 2a + h,
et sa limite vaut 2a. Au point a = 3, la dérivée vaut 6. Un déplacement h = 0,01 prédit une hausse
d’environ 0,06 ; la hausse exacte vaut 3,012 − 9 = 0,0601.
Les règles utiles pour la suite sont : la dérivée d’une constante est zéro, celle de ax + b est a, celle de
ex est ex , et celle de ln x, pour x > 0, est 1/x. La dérivée d’une somme est la somme des dérivées.
Ces quelques règles couvrent une grande partie des opérations de nos petits exemples.
Dans train, loss.backward() calcule des dérivées de la perte par rapport aux paramètres. Il ne
remplace pas chaque poids par une infinité de petites perturbations : il utilise les règles de dérivation
des opérations composées. Nous verrons ensuite comment cela se fait.
Une pente nulle ne prouve pas qu’un point est un minimum. Pour f (x) = −x2 , la dérivée en zéro est
nulle, mais zéro est un maximum. L’information de premier ordre est locale et doit être interprétée
avec prudence.
On peut estimer une dérivée en comparant deux valeurs proches, mais choisir un écart minuscule
n’est pas toujours plus fiable sur ordinateur. Les arrondis peuvent masquer la différence entre les
deux résultats. La dérivation des opérations évite cette soustraction fragile et fournit directement les
sensibilités des calculs effectivement composés.
Exercice. Pour f (w) = (w − 3)2 , calculer f ′ (1). Prévoir l’effet d’un déplacement de 1 vers 1,1, puis
comparer avec les valeurs exactes.
Correction détaillée. On développe f (w) = w2 − 6w + 9, donc f ′ (w) = 2w − 6 et f ′ (1) = −4. La
variation prévue est 0,1 × (−4) = −0,4. La perte passe exactement de 4 à 3,61, soit une variation de
−0,39 : l’approximation indique correctement le sens de l’amélioration.

Fiche 21 — Règle de chaîne : dériver une composition
/home/runner/work/SHOKOBO/SHOKOBO/mini_gpt/04_transformer.py

FeedForward.forward

Objectif. Propager une petite variation à travers plusieurs calculs successifs.
Une composition applique une fonction au résultat d’une autre. Si u = g(x) puis y = f (u), on écrit
y = f (g(x)). Une petite variation de x modifie d’abord u, puis cette modification se répercute sur y.
La règle de chaîne multiplie ces deux sensibilités locales :
                              dy   dy du
                                 =       ,        (f ◦ g)′ (x) = f ′ (g(x))g ′ (x).
                              dx   du dx
La notation ressemble à une simplification de fractions, mais elle exprime une règle de dérivation.
Le point auquel chaque dérivée est évaluée compte : f ′ s’évalue à la valeur intermédiaire g(x), pas
automatiquement à x. Cette règle suppose que les fonctions rencontrées soient dérivables aux points
utilisés pendant le calcul.
Considérons u = 3x − 1, puis y = u2 . On a du/dx = 3 et dy/du = 2u, donc dy/dx = 6(3x − 1).
À x = 2, l’intermédiaire vaut 5 et la dérivée finale vaut 30. Développer y = 9x2 − 6x + 1 donne
également 18x − 6 = 30, ce qui vérifie le calcul par une autre voie.
À comprendre. Les variables intermédiaires rendent les calculs lisibles.
Au lieu de dériver une expression immense, on conserve les résultats de chaque opération. Pour
a = wx + b, h = ϕ(a), z = vh + c, la sensibilité de z à w, les autres valeurs étant fixées, est vϕ′ (a)x.
On retrouve les facteurs du trajet w → a → h → z.
FeedForward.forward applique une séquence : couche affine, GELU, couche affine, puis dropout.
Les fonctions réellement utilisées ont leurs règles de dérivation. Notre carré u2 est seulement un
exemple facile à calculer, pas la définition de GELU.
Si plusieurs trajets relient une variable à la sortie, leurs contributions s’ajoutent. Pour y = x2 + x, la
branche carrée apporte 2x et la branche directe apporte 1. La dérivée totale est 2x + 1. Cette idée
éclairera plus tard les additions résiduelles du Transformer.
La variable par rapport à laquelle on dérive doit toujours être annoncée. Dans a = wx + b, dériver
par rapport à x donne w, tandis que dériver par rapport à w donne x. Le biais est constant dans
ces deux calculs, mais sa dérivée vaut un lorsqu’on dérive par rapport à b. Une même expression
possède donc plusieurs sensibilités, selon la question posée.
Des produits répétés de petites sensibilités peuvent atténuer fortement une variation ; de grandes
sensibilités peuvent l’amplifier. Ce constat arithmétique prépare l’étude des réseaux profonds, sans
remplacer l’analyse de leurs valeurs réelles.
Exercice. Dériver f (x) = ln(1 + ex ) en nommant ses intermédiaires. Quelle est la dérivée en zéro ?
Correction détaillée. Posons u = ex , v = 1 + u, puis f = ln v. Les sensibilités sont du/dx = ex ,
dv/du = 1 et df /dv = 1/v. Leur produit vaut f ′ (x) = ex /(1 + ex ). En zéro, e0 = 1, donc f ′ (0) = 1/2.

Fiche 22 — Gradient : une dérivée pour chaque paramètre

train

Objectif. Étendre la pente d’une courbe à une perte dépendant de plusieurs nombres.
Un réseau possède de nombreux paramètres, regroupés symboliquement dans θ = (θ0 , . . . , θn−1 ). Sa
perte J (θ) reste un seul nombre. La dérivée partielle ∂J /∂θi mesure l’effet local du paramètre i
lorsque les autres sont maintenus fixes. Le symbole ∂ rappelle cette convention.
Le gradient rassemble toutes ces dérivées dans le même ordre que les paramètres. Il indique comment
une petite modification simultanée se répercute au premier ordre :
                                        ∂J         ∂J
                                                         
                            ∇J =            ,...,       ,     ∆J ≈ ∇J · ∆θ.
                                        ∂θ0       ∂θn−1

Nous retrouvons le produit scalaire : chaque variation est pondérée par sa sensibilité, puis toutes les
contributions s’additionnent.
Pour J (a, b) = (a + 2b − 3)2 , la règle de chaîne donne les dérivées 2(a + 2b − 3) et 4(a + 2b − 3).
Au point (0, 0), le gradient est (−6, −12). Une perturbation (0,01, 0) prévoit une baisse de 0,06 ; la
perturbation (0, 0,01) prévoit une baisse de 0,12. Les deux paramètres n’ont pas la même influence
locale.
À comprendre. Le gradient des logits possède une forme particulièrement simple.
Pour la perte d’une cible y étudiée précédemment, la dérivation du logarithme de la somme donne :
                                              ∂ℓ
                                                  = pi − 1i=y .
                                              ∂zi
L’indicatrice 1i=y vaut un pour la cible, zéro sinon. Le terme pi vient de ezi / j ezj , et la dérivée de
                                                                                P

−zy fournit le terme négatif. Augmenter le logit correct diminue ainsi localement la perte, tandis
qu’augmenter un concurrent l’augmente.
Dans train, loss.backward() propage ces sensibilités jusqu’aux paramètres. Leur attribut grad
possède leur forme : une matrice de poids reçoit une matrice de dérivées. Pour une perte moyenne sur
plusieurs positions, les contributions sont additionnées puis divisées par leur nombre. Les identifiants
entiers ne sont pas les paramètres à ajuster.
Un poids partagé intervient à plusieurs positions. Sa dérivée totale additionne les contributions de
toutes ces utilisations : on n’apprend pas une copie indépendante du poids pour chaque token. Cette
accumulation explique aussi pourquoi les anciennes valeurs de grad doivent être effacées lorsqu’on
commence une nouvelle mise à jour sans accumulation volontaire.
Exercice. Avec p = (0,2, 0,5, 0,3) et une cible d’identifiant 2, calculer le gradient par rapport aux
logits, puis la somme de ses coordonnées.
Correction détaillée. Le gradient vaut (0,2, 0,5, −0,7), de somme zéro. Une translation commune
de tous les logits a donc une variation de perte nulle au premier ordre. Cela concorde avec l’invariance
exacte du softmax démontrée précédemment.

train

Objectif. Effectuer un passage avant et un passage arrière sans traiter la dérivation automatique
comme une magie.
Construisons un réseau scalaire pédagogique. Son entrée est x, ses paramètres sont w, b, v, c, et ses
deux logits sont (z, 0). La cible est le premier token, d’identifiant zéro. La fonction carrée remplace
volontairement GELU pour permettre un calcul intégral à la main ; l’entropie croisée reste celle

                     a = wx + b,        h = a2 ,     z = vh + c,   ℓ = ln(1 + e−z ).

La dernière formule vient de − ln(ez /(ez + 1)). Le logit du deuxième token reste fixé à zéro : ce n’est
pas un paramètre supplémentaire. Nous choisissons x = 2, w = 1, b = −1, v = 2, c = −2.
À comprendre. Passage avant : mémoriser les intermédiaires.
On calcule successivement a = 1 × 2 − 1 = 1, h = 12 = 1, puis z = 2 × 1 − 2 = 0. Les deux logits sont
donc nuls, les probabilités valent (1/2, 1/2) et la perte vaut ln 2 ≈ 0,6931. Ces valeurs intermédiaires
serviront dans les dérivées.
Le passage arrière commence à la perte. La dérivée par rapport à z vaut −1/(1 + ez ), donc −1/2
ici. Pour l’opération z = vh + c, on multiplie ce signal par la dérivée locale correspondant à chaque
entrée : ∂ℓ/∂v = (−1/2)h = −1/2, ∂ℓ/∂c = −1/2, et ∂ℓ/∂h = (−1/2)v = −1.
À travers le carré, on obtient ∂ℓ/∂a = (−1) × 2a = −2. La première couche affine reçoit alors ce
signal :
                         ∂ℓ                     ∂ℓ              ∂ℓ
                            = −2x = −4,            = −2,           = −2w = −2.
                         ∂w                     ∂b              ∂x
Le gradient des quatre paramètres, dans l’ordre (w, b, v, c), est donc (−4, −2, −1/2, −1/2). La dérivée
de l’entrée a été calculée pour suivre toute la chaîne, mais l’entrée observée ne doit pas être modifiée
pour apprendre les paramètres.
Dans train, loss.backward() automatise ce parcours inverse pour le vrai graphe du MiniGPT.
Chaque opération transmet une sensibilité locale ; les chemins partagés additionnent leurs contri-

l’optimiseur.
La valeur initiale du signal arrière est un : la dérivée de la perte par rapport à elle-même vaut un.
Chaque étape conserve ensuite les paramètres aux valeurs utilisées pendant le passage avant. Si l’on
changeait un poids au milieu de ce parcours, les dérivées locales ne décriraient plus toutes le même
réseau et le gradient obtenu perdrait sa cohérence.

Fiche 26 — Texte Unicode, octets et vocabulaire

train_tokenizer

Objectif. Distinguer ce que l’on voit, ce que Python compte et ce que le disque stocke.
Un texte Python de type str est une suite de points de code Unicode. Un fichier UTF-8 est une
suite d’octets. Un octet possède 256 valeurs possibles ; un point de code peut demander plusieurs
octets lors de son encodage UTF-8. Ni l’un ni l’autre ne correspond toujours à une lettre visuelle
complète : un accent combinant ou plusieurs signes composant un emoji peuvent participer à un
seul graphème perçu par le lecteur.
À comprendre. La longueur dépend de l’unité choisie.
Le texte composé de « A », « é » et du caractère U+1F642 contient trois points de code. En UTF-8,
leurs tailles respectives sont un, deux et quatre octets. On obtient donc :

                               Ncaractères = 3,      Noctets = 1 + 2 + 4 = 7.

Le tokenizer caractère produit ici trois IDs, mais leur stockage ultérieur en entiers de huit octets
occupera vingt-quatre octets, hors métadonnées. Transformer du texte en nombres n’est donc pas
automatiquement le compresser. La tokenisation prépare une interface pour le modèle ; sa taille
disque dépend également du type numérique choisi.
À comprendre. Aucune normalisation Unicode n’est appliquée.
Un « é » précomposé est un seul point de code ; un « e » suivi d’un accent aigu combinant en
comporte deux. Ces formes peuvent sembler identiques à l’écran, mais set(text) et encode les
traitent différemment. Le code ne les convertit pas vers une forme commune, ne met pas le texte en
minuscules et ne retire pas les espaces. Une politique de nettoyage serait une décision supplémentaire,
absente de cette implémentation.
Le vocabulaire est une association entre unités et entiers, pas un dictionnaire de définitions linguis-
tiques. Sa taille est notée V . Un ID valide appartient à {0, . . . , V − 1}. L’ID d’une lettre n’exprime
ni sa fréquence ni sa proximité avec une autre lettre : ces entiers désigneront des lignes d’une table
d’embeddings. La dimension D de cette table sera une autre quantité, étudiée ensuite.
Point de vigilance. Dans ce chapitre, « caractère » désigne le point de code manipulé par Python,
sauf mention explicite d’un graphème.
Cette convention rend les calculs reproductibles, notamment pour le découpage du corpus. Compter
les octets du fichier ne suffit pas à retrouver la frontière de validation calculée en caractères.

construit le même type de tokenizer. L’ordre des blocs ne change pas les IDs si leur ensemble de
caractères reste identique. Le paramètre vocab_size est ignoré dans cette branche : on ne tronque
pas l’alphabet à une taille demandée.
Point de vigilance. Le marqueur spécial est une chaîne entière.
Lorsque le corpus contient littéralement les cinq caractères de <unk>, le mode caractère les parcourt
séparément. Ils ne sont pas reconnus comme une occurrence magique du token spécial. Le retrait
dans le constructeur évite surtout de dupliquer ce marqueur si un vocabulaire fourni le contient déjà
comme entrée.
Exercice. Construire le vocabulaire de « cabac », puis encoder « bac ». Que change une demande

Fiche 28 — Encoder, décoder et perdre une information
/home/runner/work/SHOKOBO/SHOKOBO/mini_gpt/01_tokenizer.py

SimpleTokenizer

Objectif. Savoir quand l’aller-retour restitue le texte et quand il ne le peut pas.
Encoder consiste à parcourir le texte caractère par caractère. Pour chacun, stoi.get(char, unk_id)
fournit soit son ID connu, soit zéro. Décoder parcourt les IDs, cherche les tokens correspondants, puis
concatène leurs représentations. Dans cette dernière opération, l’entrée spéciale <unk> est rendue
par un point d’interrogation.
À comprendre. L’aller-retour est exact sur l’alphabet connu.
Construisons le tokenizer avec le texte original « ab a ». Sa table est [’<unk>’, ’ ’, ’a’, ’b’].
L’encodage de « ba a » donne [3, 2, 1, 2], dont le décodage redonne exactement « ba a ». L’espace
fait partie des données au même titre que les lettres. Il n’est ni supprimé ni reconstruit par une règle
grammaticale.

                    decode(encode(s)) = s      si tous les caractères de s sont connus.

En revanche, « bz » devient [3, 0], puis « b ? ». Une chaîne « bΩ » suit le même trajet. Deux
entrées distinctes ayant la même image, aucune fonction de décodage ne peut déterminer quel
caractère inconnu était présent. Cette perte n’est pas une erreur du réseau : elle se produit avant son
intervention. Elle illustre une application non injective, notion mathématique utile pour comprendre
les limites d’une représentation.
À comprendre. Les méthodes d’inspection ne rendent pas toutes la même chaîne.
id_to_token(0) retourne le marqueur <unk>, tandis que decode([0]) retourne ?. De même, un
entier négatif ou supérieur au dernier indice valide est converti en marqueur inconnu lors du décodage.
Le test de borne empêche notamment qu’un indice négatif sélectionne le dernier élément, comme le
ferait habituellement une liste Python.
Point de vigilance. Un vrai point d’interrogation peut lui-même appartenir au vocabulaire.
L’affichage décodé ne permet alors pas de distinguer ce caractère d’un inconnu remplacé. Pour
mesurer les inconnus, il faut compter unk_id dans les IDs, pas compter les points d’interrogation
du texte reconstruit. Le taux obtenu décrit la couverture de l’alphabet d’entraînement. Sur une
validation contenant une nouvelle écriture, il peut être élevé, même si le programme fonctionne
exactement comme prévu.
Exercice. Avec le vocabulaire précédent, décoder [2, −1, 99, 3], puis donner le résultat de
id_to_token(-1). Peut-on retrouver les inconnus ?
Correction détaillée. Le texte est « a ? ?b ». La méthode d’inspection retourne <unk>. Les deux IDs
invalides ne révèlent aucun caractère initial ; le décodage fournit une représentation de remplacement,
pas une réparation. Il faut conserver le texte brut si cette information doit rester accessible.

Objectif. Comprendre pourquoi les poids du modèle ne suffisent pas à interpréter ses IDs.

À comprendre. Un état compact suffit pour le mode caractère.

Fiche 30 — BPE : apprendre des fusions, à la main
/home/runner/work/SHOKOBO/SHOKOBO/mini_gpt/01_tokenizer.py

train_tokenizer

Objectif. Comprendre le principe des paires fréquentes avant les détails de la bibliothèque.
Le mode caractère impose une position par caractère. BPE cherche à représenter des suites fréquentes
par des unités plus longues. Son nom, Byte Pair Encoding, rappelle une méthode fondée sur le
regroupement de paires. Pour isoler cette idée, travaillons d’abord sur une version jouet dont les
symboles initiaux sont des lettres. La version byte-level du dépôt sera précisée à la fiche suivante.
À comprendre. Une fusion remplace deux symboles adjacents par un nouveau symbole.
Considérons trois occurrences séparées du mot inventé « baba ». Chaque occurrence commence
comme [b, a, b, a]. Au total, la paire (b, a) apparaît six fois et la paire (a, b) trois fois. On choisit donc
(b, a), puis chaque occurrence devient [ba, ba]. La paire (ba, ba) apparaît maintenant trois fois : une
seconde fusion produit le symbole [baba].

                                    [b, a, b, a] −→ [ba, ba] −→ [baba].

Les frontières entre occurrences sont ici imposées : on ne compte pas de paire reliant la fin d’une
occurrence au début de la suivante. Cette hypothèse explicite évite d’attribuer au calcul des paires
inexistantes dans l’exemple.
La taille de la séquence diminue, tandis que le vocabulaire gagne des entrées. Les anciens symboles
restent utiles pour des mots différents. Si l’on rencontre « bac », la fusion apprise (b, a) permet [ba, c],
mais le symbole baba ne s’applique pas à toute la chaîne. Apprendre BPE ne revient donc pas à
enregistrer seulement une liste de mots.
À comprendre. L’ordre des fusions fait partie de l’apprentissage.
Lorsqu’on ajoute une fusion, les comptages pertinents évoluent. Des égalités de fréquence peuvent
nécessiter une règle de départage. Notre exemple possède des maxima simples ; il ne prétend pas
prédire les IDs ni toutes les décisions internes de la bibliothèque. Le code du dépôt délègue ces
mécanismes à tokenizers, au lieu de réimplémenter les compteurs et leurs mises à jour.
Point de vigilance. La compression n’est pas un score de compréhension.
Un symbole long très fréquent peut économiser des positions sans porter un sens linguistique stable.
Le Transformer apprendra ensuite à prédire les unités obtenues. Changer de tokenizer change aussi
l’unité de sa perte.
Exercice. Avec deux occurrences de « abac », compter les paires initiales. Si l’on impose de fusionner
(a, b), quelle représentation obtient-on ?
Correction détaillée. Les paires (a, b), (b, a) et (a, c) apparaissent chacune deux fois : il y a égalité,
donc aucune fusion unique n’est déductible des seules fréquences. Avec le choix imposé, chaque
occurrence devient [ab, a, c], soit trois tokens au lieu de quatre.

Fiche 31 — BPE byte-level : partir des 256 octets

BPETokenizer

Objectif. Expliquer pourquoi un caractère absent de l’apprentissage reste représentable.
Dans le dépôt, le BPE n’apprend pas seulement sur l’alphabet des lettres rencontrées. Son prétrai-
tement est ByteLevel(add_prefix_space=False) et son alphabet initial contient les 256 valeurs
d’octet. La bibliothèque représente ces octets par des symboles internes ; les tokens affichés ne doivent
donc pas toujours être lus comme des fragments ordinaires de texte Unicode.
À comprendre. Couverture des octets et couverture des caractères sont différentes.
Un emoji absent du texte d’entraînement possède néanmoins une représentation UTF-8 constituée
d’octets. Ces octets sont couverts par l’alphabet initial, même lorsqu’aucune fusion apprise ne les
regroupe. L’encodage peut être plus long que pour un motif fréquent, mais le décodage byte-level
peut reconstituer le caractère. C’est une différence fondamentale avec le remplacement par unk_id
du tokenizer caractère.
Le formateur BPE conserve aussi <unk> comme token spécial. Le vocabulaire dispose donc d’un
plancher :
                                    V ≥ 256 + 1 = 257.
Demander vocab_size=100 ne supprime pas les octets nécessaires : la taille réelle peut dépasser
la demande. Inversement, demander une grande taille ne garantit pas assez de motifs utiles pour
l’atteindre. Le modèle doit utiliser tokenizer.vocab_size, propriété effective du backend, et non
supposer que la valeur demandée est la taille obtenue.
À comprendre. L’absence de normalisation est un choix concret.
Aucun normaliseur n’est installé. L’option de préfixe est désactivée : on n’ajoute pas une espace
artificielle au début du texte. Le décodeur ByteLevel accompagne le pré-tokenizer. L’encodage utilise
add_special_tokens=False et le décodage skip_special_tokens=False. Ces réglages préservent
notamment le traitement explicite du marqueur littéral étudié par les tests. Cela ne promet pas
qu’une suite arbitraire d’IDs produite par un modèle forme toujours des octets UTF-8 valides.
Point de vigilance. La dépendance BPE est facultative, pas implicite.
_bpe_library importe tokenizers seulement à la demande. Le parcours caractère n’en a
pas besoin. Son installation est décrite dans /home/runner/work/SHOKOBO/SHOKOBO/mini_gpt/
requirements-bpe.txt. La restauration d’un état BPE exige elle aussi cette bibliothèque, même si
aucun nouvel apprentissage du tokenizer n’est prévu.
Exercice. Un tokenizer BPE appris sur des lettres latines reçoit « Ω ». Faut-il ajouter obligatoirement
cette lettre au vocabulaire ? Que représente la borne 257 ?
Correction détaillée. Non : les octets UTF-8 de « Ω » sont déjà représentables. Une fusion
spécifique pourrait raccourcir sa représentation, sans être nécessaire à sa couverture. La borne
compte 256 symboles d’octet et le token spécial ; elle ne compte pas 257 caractères Unicode différents.

BPETokenizer

Objectif. Comprendre ce qui est sauvegardé et pourquoi deux encodages du même texte peuvent
différer.
Pour BPE, une simple liste de caractères serait insuffisante. Il faut conserver le vocabulaire appris, les
règles de fusion et la configuration du traitement des octets. BPETokenizer.to_state renvoie donc
kind: ’bpe’ et tokenizer_json, une sérialisation complète du backend. tokenizer_from_state
la recharge avec Tokenizer.from_str, sans recommencer l’apprentissage.
À comprendre. Restaurer le tokenizer ne restaure pas automatiquement toutes les conditions
d’encodage.
L’état décrit le backend. La taille des blocs de lecture utilisés par prepare_corpus appartient, elle,
au code de préparation. Pour reproduire exactement les fichiers d’IDs, il faut conserver le texte, son
découpage brut, le tokenizer et la stratégie de blocs. L’égalité des textes décodés est un critère moins
strict que l’égalité des séquences d’entiers.
Imaginons, uniquement pour raisonner, qu’une fusion apprise représente ab par un seul token.

peut pas appliquer cette fusion à travers les appels. Les deux listes concaténées contiennent alors
deux IDs.
                       E(u v) ̸= E(u) ∥ E(v) peut se produire avec BPE.
Le symbole ∥ désigne la concaténation de listes, non une addition. Dans les deux cas, le décodage
des IDs issus du texte peut reconstituer ab. Une représentation différente n’implique donc pas
nécessairement une information textuelle perdue.
À comprendre. Deux types de frontières interviennent dans le pipeline.
Les blocs d’apprentissage interdisent certaines fusions lors de leur acquisition. Les blocs d’encodage
interdisent ensuite d’appliquer une fusion à cheval sur deux appels. Enfin, la frontière entre entraîne-
ment et validation est respectée séparément : aucun appel ne fusionne un morceau de train avec un
morceau de validation.
Point de vigilance. Une frontière de tokenisation n’est pas une réinitialisation du modèle.
Les IDs des blocs successifs d’un même split sont écrits à la suite. Les fenêtres du dataset pourront
donc traverser ces anciennes frontières. Aucun token séparateur n’est ajouté pour les signaler. Seule
la séparation entre les deux fichiers interdit une fenêtre mélangeant train et validation.
Exercice. Deux préparations emploient le même état BPE mais des blocs de 4096 et 2048 caractères.

Correction détaillée. Non. Les frontières supplémentaires peuvent empêcher des fusions et changer

sont identiques, les fenêtres en tokens et les quantités de contexte textuel qu’elles couvrent peuvent
différer.

Fiche 34 — Autorégression : une entrée, sa cible décalée

NextTokenDataset

Objectif. Transformer une suite d’IDs en questions de prédiction sans créer d’étiquettes manuelles.
L’autorégression apprend à prédire le prochain élément à partir des précédents. Dans un texte,
chaque token observé peut devenir la cible du token situé juste avant lui. Les données fournissent
ainsi leurs propres réponses : on parle d’apprentissage auto-supervisé. Il ne s’agit pas de demander à
un humain de classer chaque phrase, mais de réorganiser un texte déjà disponible.
À comprendre. Une fenêtre de longueur T demande T + 1 tokens sources.
Notons z0 , . . . , zN −1 les IDs du split. Pour un départ i, on prépare :

                               Xt = zi+t ,      Yt = zi+t+1 ,    0 ≤ t < T.

La longueur maximale de contexte du modèle est notée C. Les datasets de ce dépôt construisent des
fenêtres fixes de taille T = C, même si la notation distingue utilement longueur courante et capacité
maximale. Ni T ni C n’est la taille V du vocabulaire.
Prenons la suite artificielle [4, 7, 2, 9, 5] et T = 3. Au départ zéro, X = [4, 7, 2] et Y = [7, 2, 9]. La
première position doit prévoir 7 après avoir reçu 4. La deuxième peut utiliser 4 et 7 pour prévoir 2.
La troisième peut utiliser 4, 7 et 2 pour prévoir 9. Le token 5 n’intervient pas dans cette première
fenêtre, mais apparaîtra dans la cible de la fenêtre suivante.
À comprendre. Le décalage seul ne garantit pas la causalité.
Les cibles sont justes, mais un réseau sans masque pourrait regarder Xt+1 , qui est précisément
Yt . Il disposerait de la réponse à l’intérieur de l’entrée. Le masque causal étudié dans le chapitre
Transformer empêche cette consultation du futur. Ici, nous préparons les bonnes paires ; le modèle
devra encore respecter la bonne circulation d’information.
Point de vigilance. On ne tire pas de nouveaux tokens pour construire Y .
Les cibles viennent du corpus observé. Pendant l’entraînement, les entrées sont également les vrais
tokens du texte, pas les prédictions précédentes du réseau. La génération fonctionnera autrement : le
modèle réinjectera ses propres sorties lorsqu’aucun texte futur n’est fourni. Cette différence explique
pourquoi une erreur générée peut modifier tout le contexte suivant.
Exercice. Avec [8, 1, 6, 3] et T = 3, écrire les paires et expliquer pourquoi utiliser Y = X ne convient
pas.
Correction détaillée. On obtient X = [8, 1, 6] et Y = [1, 6, 3]. Choisir Y = X demanderait de
recopier le token courant au lieu de prévoir le suivant. Le dernier token 3 est une cible valable
précisément parce qu’un quatrième token source est disponible.

NextTokenDataset

Objectif. Retrouver la formule de longueur à partir des indices admissibles.
NextTokenDataset garde une liste d’IDs et une longueur de contexte. Il ne fabrique pas d’avance une
liste contenant toutes les fenêtres. À chaque appel, deux tranches de la liste source sont converties

À comprendre. Le dernier indice de la cible impose la borne.

la liste de longueur N , dont le dernier indice est N − 1. Par conséquent :

                          0 ≤ i ≤ N − C − 1,         M = len(dataset) = N − C.

Le nombre d’entiers entre zéro et N − C − 1, bornes incluses, est bien N − C. Ce « plus un » du

la formule.

dernière a X = [2, 3, 4, 5] et Y = [3, 4, 5, 6]. Un départ 3 demanderait une cible d’indice 7, inexistante.
Si l’on réduit le contexte à deux, le nombre de fenêtres passe à cinq, mais chaque prédiction dispose
de moins d’historique.
À comprendre. Les fenêtres se recouvrent fortement.
Deux départs voisins partagent presque tous leurs tokens. Ils ne sont donc pas des observations
indépendantes. Un token central peut contribuer à plusieurs cibles avec des préfixes différents. Ce
recouvrement est voulu pour exploiter le texte ; il faudra cependant éviter de disperser de telles
fenêtres entre entraînement et validation.
Point de vigilance. Cette classe reste volontairement peu défensive.
Le constructeur vérifie que la liste est plus longue que le contexte. Il n’effectue pas les validations
détaillées de type, de positivité ou de bornes présentes dans MemmapTokenDataset. En particulier, il
ne faut pas supposer que les indices négatifs reproduisent le comportement du dataset memmap : les
tranches Python peuvent donner des fenêtres vides ou tronquées. Dans l’usage normal, le chargeur
parcourt les indices valides de zéro à M − 1.

Correction détaillée. On obtient sept fenêtres, puis une seule. Avec C = 12, il manque le treizième

evaluate

Objectif. Lire une forme [B, T ] et traiter correctement le dernier lot.
Un dataset répond à la question « quel exemple correspond à cet indice ? ». Un DataLoader choisit
des indices, récupère les exemples, puis les regroupe. Avec des fenêtres de même longueur, la collation
standard empile les entrées dans un tenseur X et les cibles dans un tenseur Y . La dimension de
batch B compte les fenêtres simultanées ; T compte les positions dans chacune.
À comprendre. Un batch ne concatène pas les fenêtres en une phrase.
Si deux exemples sont [1, 2, 3] et [4, 5, 6], l’entrée du batch possède deux lignes et trois colonnes, non
une ligne de six positions. Le modèle traite chaque ligne comme une séquence distincte. La suite
d’une ligne n’est pas le début de la suivante ; aucun contexte linguistique ne traverse la dimension de
batch.
                                        X, Y ∈ {0, . . . , V − 1}B×T .
Les entrées restent des IDs entiers, pas des vecteurs d’embedding. La dimension D apparaîtra
seulement quand le modèle cherchera les représentations associées à ces IDs.
Supposons dix fenêtres et une taille demandée B = 4. Comme les chargeurs du dépôt ne demandent
pas drop_last=True, ils produisent des lots de quatre, quatre et deux fenêtres. Le dernier tenseur
a donc la forme [2, T ]. Une taille demandée ne garantit pas une taille effective constante en fin de
parcours. Le nombre de lots est le plafond de M/B.
À comprendre. Une moyenne de pertes doit tenir compte du nombre de cibles.
La fonction evaluate multiplie la perte moyenne du lot par y.numel(), accumule cette somme, puis
divise par le nombre total de cibles. Un petit lot n’a ainsi pas le même poids qu’un grand. Avec
T fixe, pondérer par BT revient à pondérer par le nombre de fenêtres ; la formulation par token
exprime directement ce qui est prédit.
Point de vigilance. L’ordre dépend du chargeur et de son échantillonneur.
La démonstration simple et la validation utilisent un ordre séquentiel. L’entraînement actif choisit
des fenêtres avec remise. Ce choix change quelles lignes sont réunies, mais ne change pas le décalage
interne entre chaque ligne de X et sa ligne de Y .
Exercice. Pour dix fenêtres et B = 4, les pertes moyennes des trois lots sont 1, 2 et 5. Calculer la
perte globale.
Correction détaillée. Le contexte étant identique, la moyenne correcte est (4×1+4×2+2×5)/10 =
2,2. La moyenne non pondérée 8/3 surévaluerait le petit dernier lot. Le code pondère précisément
pour éviter ce biais arithmétique.

Fiche 37 — Éviter la fuite : séparer avant d’apprendre

prepare_corpus

Objectif. Définir une validation qui n’a participé ni au vocabulaire appris ni aux fenêtres d’entraî-
nement.
La validation doit mesurer le comportement sur une portion tenue à l’écart de l’apprentissage. Une
fuite de données apparaît quand une information de cette portion influence la construction du
système évalué. La fuite ne se limite pas aux poids du réseau : choisir des fusions BPE à partir du
texte de validation utilise déjà ses régularités.
À comprendre. La séparation intervient sur le texte brut.
Pour Ncar caractères et une fraction f , le code calcule la longueur d’entraînement par int(total *
(1 - validation_fraction)). Pour cette quantité positive, l’intention mathématique est :

                             ntrain = ⌊Ncar (1 − f )⌋,     nval = Ncar − ntrain .

L’implémentation effectue le produit en virgule flottante : près d’une frontière entière, il faut reprendre
son calcul exact pour reproduire le découpage. Les nombres ci-dessus comptent des caractères, pas
les IDs BPE qui n’existent pas encore.
Le préfixe sert à apprendre le tokenizer. Les deux portions sont ensuite encodées séparément avec ce
même tokenizer et écrites dans deux fichiers. Les fenêtres sont enfin construites indépendamment dans
chacun. Aucune fenêtre ne franchit la séparation. Les caractères du suffixe peuvent naturellement
exister aussi dans le préfixe : « disjoint » signifie ici positions sources distinctes, pas alphabets sans
intersection.
Prenons « abcabcZZ » et f = 0,25. Six caractères vont au train, deux à la validation. Le vocabulaire
caractère apprend seulement a, b et c, plus l’inconnu. Les deux Z deviennent donc deux IDs zéro. Les
apprendre dans le vocabulaire avant la séparation masquerait cette nouveauté réelle. Cet exemple
exact fait partie des tests du dépôt.
Point de vigilance. Découper des fenêtres déjà créées est une mauvaise protection.
Deux fenêtres voisines se recouvrent. Si on en envoie une au train et l’autre en validation, une
grande partie du passage évalué a déjà été utilisée. Le découpage brut avant fenêtrage élimine ce
mécanisme, mais pas une répétition du même document à deux endroits du corpus. La déduplication
des contenus constitue un contrôle supplémentaire, non réalisé par cette fonction.
Exercice. Un collègue apprend BPE sur tout le texte, puis sépare parfaitement les fenêtres en deux
fichiers. La validation est-elle totalement tenue à l’écart ?
Correction détaillée. Non. Même sans fenêtre commune, le vocabulaire et les fusions ont exploité
les fréquences de validation. Il faut d’abord séparer le brut, apprendre BPE sur le préfixe seulement,
puis encoder le suffixe sans modifier le tokenizer. L’évaluation porte ainsi sur une représentation
fixée avant de voir ce suffixe.

prepare_corpus

Objectif. Interpréter un score en fonction de l’ordre du corpus, sans confondre séparation et
représentativité.
Le pipeline réserve la dernière fraction du texte à la validation. Ce découpage contigu conserve
l’ordre local et évite le mélange de fenêtres voisines entre les deux ensembles. Il possède cependant
une conséquence : la validation représente la fin du fichier, pas nécessairement la population de
textes à laquelle on souhaite appliquer le modèle.
À comprendre. Une distribution peut changer le long du document.
Imaginons un corpus original constitué de descriptions d’objets, suivies d’instructions techniques.
Avec une coupure près du changement de thème, le modèle apprend surtout sur des descriptions
et est évalué sur des consignes. Sa perte reflète alors à la fois l’apprentissage et ce changement de
domaine. Une validation difficile n’indique pas automatiquement un défaut d’optimisation ; elle peut
signaler que la tâche évaluée diffère de la tâche entraînée.
À l’inverse, un suffixe répétant presque mot pour mot le début peut rendre la validation artificiellement
facile. Les positions sont disjointes, mais le contenu ne l’est pas vraiment. Le code ne détecte ni
doublons de documents ni versions proches.
À comprendre. La proportion brute n’est pas toujours la proportion tokenisée.

celle des caractères, à l’arrondi près. Avec BPE, des régions très répétitives peuvent être davantage
regroupées. Une validation de 10 % des caractères ne garantit donc pas 10 % des tokens, ni 10 % des
fenêtres. Pour un contexte C et un pas un, chaque split perd en outre C départs par rapport à son
nombre de tokens.
Point de vigilance. On ne doit pas corriger le biais en réutilisant silencieusement le train.
Le dépôt refuse les portions trop courtes ; il ne remplace pas la validation par des exemples
d’entraînement. Pour une expérience mieux équilibrée, on peut préparer en amont un ordre de
documents adapté à la question étudiée, en conservant des groupes indépendants. Cette opération
extérieure au pipeline doit être consignée. Une séparation chronologique convient aussi pour évaluer
la prévision de textes futurs.
Exercice. Un fichier de 10 000 caractères possède un suffixe de 1000 caractères dans une écriture
absente du préfixe. Que prévoir en mode caractère ?
Correction détaillée. Avec une fraction de 0,1, ce suffixe sert à la validation. Les caractères non
observés deviennent inconnus ; le score porte donc en partie sur la prédiction du marqueur zéro, pas
sur la restitution de cette écriture. Il faut rapporter la couverture du vocabulaire pour interpréter
honnêtement la perte.

Fiche 39 — Lire par blocs Unicode : les trois passages

_text_chunks

Objectif. Comprendre une lecture bornée qui préserve les fins de ligne.
_text_chunks ouvre le fichier avec encoding=’utf-8’ et newline=”. Il demande au lecteur texte
des blocs d’au plus 4096 caractères. Le décodage UTF-8 est assuré par Python : la fonction n’effectue
pas de découpage arbitraire dans les octets d’un caractère multioctet. Une ligne gigantesque reste
donc lue par morceaux, au lieu d’être chargée intégralement avec un itérateur de lignes.
À comprendre. Les positions comptent des caractères déjà décodés.
La variable position avance de len(chunk). Si une borne stop est fournie, la prochaine demande
de lecture est réduite pour ne pas la dépasser. La borne start supprime la partie initiale des blocs
qui précède la zone souhaitée. Elle ne déclenche pas un saut direct à un offset binaire : le fichier est
lu depuis son début, puis les caractères antérieurs sont ignorés.
Par exemple, prenons les cinq caractères « a », « é », U+1F642, « b », « c ». La plage [1, 4[ sélectionne
« é », U+1F642 et « b ». Chercher directement les octets de positions 1 à 4 ne produirait pas cette
même sélection. L’option newline=” laisse subsister les caractères \r et \n au lieu de convertir une
paire CRLF en un unique saut de ligne. Cette fidélité concerne la lecture ; le mode caractère peut
encore remplacer un signe absent de son alphabet.
À comprendre. La préparation organise trois passages logiques.
Le premier compte tous les caractères pour déterminer la coupure. Le deuxième fournit le préfixe au
tokenizer ; en BPE, son budget peut arrêter cette consommation avant la fin du préfixe. Le troisième
relit tout le corpus et écrit les IDs des deux splits, en coupant exactement le bloc qui contient leur
frontière. Cela évite de conserver en RAM une copie complète du texte.
Point de vigilance. La source doit rester stable entre ces lectures.
Si un autre processus ajoute, retire ou modifie du texte, le comptage, le vocabulaire et les IDs
peuvent ne plus décrire le même corpus. Le programme ne prend pas de cliché immuable et ne vérifie
pas une empreinte entre les passages. « Trois passages » décrit une stratégie de mémoire, pas un
protocole de synchronisation avec des rédacteurs concurrents. Le coût d’entrées-sorties demeure réel,
même quand la mémoire est bornée.
Exercice. Une fin de fichier contient « A » suivi de CRLF puis « é ». Combien de caractères le
comptage conserve-t-il ?
Correction détaillée. Quatre : A, retour chariot, saut de ligne et é. Les octets UTF-8 sont au
nombre de cinq. La préservation de CRLF empêche que la coupure soit calculée sur un texte
implicitement raccourci par conversion des fins de ligne.

MemmapTokenDataset

Objectif. Calculer l’espace disque et reconnaître ce que le format ne décrit pas.
La préparation convertit les IDs de chaque bloc avec np.asarray(..., dtype=np.int64), puis
écrits avec tofile. Un entier int64 occupe huit octets. Les écritures successives s’ajoutent dans le
même flux binaire ; aucun séparateur n’est nécessaire entre les blocs puisque chaque valeur possède
une taille fixe.
À comprendre. La taille donne le nombre de tokens, pas leur signification.
Pour N IDs, le volume utile du fichier est :

                                       S = 8N octets,       N = S/8.

Un million de tokens demande donc huit millions d’octets, soit environ 7,63 Mio. Les deux unités
diffèrent : un mégaoctet décimal vaut un million d’octets, tandis qu’un mébioctet vaut 220 octets.
L’état du tokenizer et les autres sorties s’ajoutent à cette estimation.
Le dataset lit la taille du fichier et refuse une longueur qui n’est pas multiple de huit. Cette vérification
détecte, par exemple, un fichier de dix-neuf octets. Elle ne détecte pas un fichier arbitraire de vingt-
quatre octets : trois groupes de huit octets peuvent être interprétés comme des entiers même s’ils ne
viennent pas du tokenizer attendu.
À comprendre. Le format est volontairement minimal.
Il n’existe ni en-tête, ni numéro de version, ni taille de vocabulaire, ni nom de tokenizer dans les
binaires. Le type NumPy est natif : l’ordre des octets dépend de la plateforme. Transférer ces fichiers
vers une architecture d’endianness différente demanderait une convention explicite ou une conversion ;
le programme ne l’effectue pas automatiquement. Sur la plateforme courante, NumPy et PyTorch
utilisent ici des entiers compatibles pour indexer les embeddings.
Point de vigilance. Taille valide ne signifie pas IDs valides.
Les IDs produits normalement sont compris entre zéro et V − 1. MemmapTokenDataset ne vérifie pas
chaque valeur contre V , qu’il ne reçoit d’ailleurs pas en argument. Une corruption ou un tokenizer
incohérent peut donc n’être découverte qu’au moment d’accéder aux embeddings, voire produire des
valeurs sémantiquement fausses sans dépasser les bornes. Conserver l’association entre données, état
et expérience reste indispensable.
Exercice. Deux splits comportent 120 000 et 30 000 tokens. Quel volume binaire total prévoir ? Un
fichier supplémentaire de 65 octets est-il un fichier d’IDs acceptable ?
Correction détaillée. Il faut 8(120 000 + 30 000) = 1 200 000 octets, sans compter le JSON ni
les checkpoints. Soixante-cinq n’est pas divisible par huit : le constructeur le refuse. Pour autant,
arrondir sa taille à 64 octets ne réparerait pas son contenu et ne garantirait aucune cohérence des
IDs.

MemmapTokenDataset

Objectif. Expliquer la mémoire économisée sans promettre une consommation nulle.
Un memory mapping associe le contenu d’un fichier à une zone adressable par le processus. Le
système d’exploitation charge les pages nécessaires au fil des accès et peut les garder en cache. Le
dataset évite ainsi de charger d’emblée tous les IDs dans une liste Python et ne mémorise pas non
plus un tableau de tous les départs de fenêtres.
À comprendre. L’ouverture est paresseuse et propre au processus courant.
Le constructeur place _tokens et _pid à None. Au premier accès, il ouvre np.memmap(...,
mode=’r’) et mémorise l’identifiant du processus avec os.getpid(). Si un accès ultérieur vient d’un
processus différent, le test d’identifiant entraîne une nouvelle ouverture. Cela importe notamment
lorsqu’un chargeur utilise plusieurs processus de travail. Le chargeur actif du dépôt ne configure
toutefois pas explicitement de workers supplémentaires.
À comprendre. Les tenseurs retournés sont des copies de fenêtres.
Les tranches X et Y sont chacune copiées avant l’appel à torch.from_numpy. PyTorch partage alors
la mémoire de ces petits tableaux copiés, pas celle du fichier mappé. Modifier un élément de X ne
modifie donc ni le fichier ni une future lecture de la même fenêtre. Les deux copies sont également
indépendantes entre elles, malgré le recouvrement des positions sources.

                          Scopies par exemple = 2 × C × 8 = 16C   octets utiles.

Cette estimation ne comprend pas les objets Python, les batches empilés, le cache du système, les
transferts vers le GPU ni les activations du modèle.
À comprendre. La sérialisation transporte une description, pas le mapping ouvert.
__getstate__ copie le dictionnaire d’attributs et remet _tokens ainsi que _pid à None dans l’état
exporté. Après restauration, le prochain accès rouvrira le fichier. Le chemin absolu doit donc encore
exister et désigner les mêmes données ; le pickle n’est pas une archive autonome du corpus.
Point de vigilance. Les fichiers doivent rester inchangés pendant leur utilisation.
Les remplacer ou les tronquer pendant qu’un dataset les consulte invalide les hypothèses de taille
et de cohérence. La lecture seule protège contre les écritures par ce mapping, pas contre un autre
programme.
Exercice. Avec C = 128, quelle taille représentent les deux copies utiles ? Une modification de x[0]

Correction détaillée. Elles représentent 16 × 128 = 2048 octets, soit 2 Kio, avant les surcoûts.
La modification reste locale à la copie retournée. Une relecture retrouve la valeur du fichier ; cette
propriété est précisément vérifiée dans les tests de mutation et de restauration du dataset.

Objectif. Interpréter une époque dans le chemin d’entraînement actuel.
L’entraînement utilise RandomSampler avec replacement=True et num_samples=len(dataset). Il
demande donc autant de tirages qu’il existe de fenêtres, mais chaque tirage peut reprendre un indice

des exemples de principe, pas des sorties annoncées pour une graine particulière du dépôt.
Si les M fenêtres ont la même probabilité à chaque tirage, la probabilité qu’une fenêtre donnée ne
soit jamais choisie lors des M tirages vaut :
                                                                  M
                                                              1
                                                         
                                          pabsente = 1 −               .
                                                              M

L’espérance du nombre de fenêtres distinctes visitées est alors M (1 − pabsente ). Pour un grand M ,
cela représente environ 63,2 % du dataset. Ce pourcentage moyen ne décrit pas une garantie pour
une époque particulière ; il résume une distribution de résultats possibles.

Son chargeur emploie shuffle=False : les fenêtres retenues par le pas sont parcourues séquentiel-

À comprendre. Deuxième seuil : les tokens encodés.

MiniGPT.token_embedding

Objectif. Passer d’un entier désignant un token à un vecteur entraînable, sans confondre le numéro
du token avec une grandeur numérique.
À comprendre. Une table d’embeddings est une matrice de paramètres. Elle possède V lignes, une
par entrée du vocabulaire, et D colonnes. Le token numéro i sélectionne sa ligne : son identifiant est
une adresse, pas une mesure de son sens.
Dans le constructeur de MiniGPT, nn.Embedding(vocab_size, embedding_dim) crée cette table.
Dans forward, self.token_embedding(x) transforme les identifiants entiers de forme (B, T ) en
nombres réels de forme (B, T, D). La longueur de la séquence ne change pas ; chaque case reçoit
maintenant D coordonnées.
On peut comprendre cette sélection avec un vecteur indicateur, aussi appelé one-hot. Il contient V
coordonnées, toutes nulles sauf celle d’indice i, égale à un. Si E désigne la table, alors

                                ei = (0, . . . , 1, . . . , 0),   hi = ei E = Ei,: .

Le produit matriciel sélectionne exactement la même ligne. PyTorch n’a toutefois pas besoin de
fabriquer tous ces zéros : l’accès indexé exprime directement l’opération voulue. Cette équivalence
sert à comprendre les mathématiques, pas à recommander une implémentation plus volumineuse.
Par exemple, prenons une table pédagogique dont les trois lignes sont (1, 0), (0, 2) et (−1, 3). La
séquence d’identifiants (2, 0, 2) devient ((−1, 3), (1, 0), (−1, 3)). Deux occurrences du même identifiant
donnent ici le même vecteur. Elles pourront devenir différentes après l’ajout des positions et le
passage dans les blocs.
La table contient V D paramètres, indépendamment de B et de T . Pendant l’apprentissage, les
occurrences d’un même token contribuent à la modification d’une seule ligne partagée. Ce partage
n’implique pas que deux tokens voisins dans la liste aient des embeddings voisins : l’ordre du
vocabulaire reste conventionnel.
Point de vigilance. Un embedding n’est pas une probabilité : ses coordonnées peuvent être négatives
et leur somme n’est pas imposée. Il est appris avec le reste du modèle, sans dictionnaire sémantique
fourni à l’avance.

Correction détaillée. La table contient 23 × 16 = 368 paramètres et la sortie a la forme (2, 8, 16),

identiques consultent la même ligne, quelle que soit leur fenêtre ; seule leur utilisation ultérieure peut
différencier leurs représentations.

MiniGPT.position_embedding

Objectif. Comprendre pourquoi MiniGPT ajoute une information de position et comment une table
unique est partagée entre toutes les fenêtres d’un lot.
À comprendre. La table des tokens ne distingue pas les occurrences d’un même identifiant. En
mode learned, une seconde table contient une ligne par position autorisée. Son rôle est de fournir
au réseau une information sur la place occupée dans la fenêtre.
Le constructeur crée nn.Embedding(context_length, embedding_dim). Cette table possède C
lignes de dimension D, donc CD paramètres. Sans cache, les positions sont les entiers de zéro à T − 1.
L’appel à unsqueeze(0) leur donne la forme (1, T ) ; la table produit alors un tenseur (1, T, D).
Les embeddings de tokens ont, eux, la forme (B, T, D). L’addition utilise le broadcasting : la dimension
initiale égale à un est compatible avec les B fenêtres. Toutes reçoivent les mêmes vecteurs positionnels
aux mêmes indices, sans créer B tables de paramètres distinctes.

                      hb,t,: = Exb,t ,: + Pt,: ,   (B, T, D) + (1, T, D) −→ (B, T, D).

La somme, et non la concaténation, conserve une largeur D. Par exemple, un token représenté par
(1, 2), placé à une position représentée par (3, −1), fournit (4, 1). À une autre position de vecteur
(0, 2), le même token fournit (1, 4). Le réseau reçoit ainsi des vecteurs différents avant toute attention.
Le code applique ensuite le dropout à cette somme. En évaluation, ce dropout est désactivé. En
entraînement, il peut masquer certaines coordonnées ; il n’efface pas des entrées de la table elle-même.
Avec un cache contenant déjà p tokens, les nouvelles positions commencent à p, pas à zéro.
Point de vigilance. En mode rope, position_embedding vaut None. MiniGPT n’ajoute alors
aucune table de positions : les rotations des requêtes et des clés fournissent une autre organisation
positionnelle. Dans les deux modes, le contrat du modèle conserve la limite C.

MultiHeadSelfAttention.q_proj

Objectif. Donner un sens opérationnel aux lettres Q, K et aux valeurs, sans attribuer au réseau des
intentions humaines.
À comprendre. Une projection linéaire transforme chaque vecteur de dimension D en un autre
vecteur. Ici, les couches q_proj, k_proj et v_proj sont trois applications affines indépendantes,
appliquées au même tenseur d’entrée.
Le mot requête désigne le vecteur utilisé du côté de la position qui reçoit de l’information. Une clé
désigne le vecteur avec lequel cette requête est comparée. Une valeur désigne le contenu numérique
ensuite combiné. Ce vocabulaire décrit trois rôles dans un calcul ; il n’affirme pas qu’un token pose
consciemment une question.
Pour une représentation ligne xt , on peut écrire, en respectant le stockage des poids de nn.Linear,

                    qt = xt WQ⊤ + bQ ,                ⊤
                                             kt = xt WK + bK ,             ⊤
                                                                  vt = xt Wval + bval .

Chaque matrice de poids a la forme (D, D), chaque biais possède D coordonnées. Les mêmes
paramètres sont utilisés à toutes les positions et pour toutes les fenêtres. Les trois résultats ont
initialement la forme (B, T, D) ; leur séparation en têtes vient ensuite.
Pour une expérience de pensée, fixons les trois matrices à l’identité et leurs biais à zéro. On obtient
trois copies de l’entrée. Cela permet de suivre les opérations, mais ce n’est pas l’initialisation du
dépôt. Les matrices réellement entraînables peuvent sélectionner des combinaisons de coordonnées
très différentes.
Les valeurs ne servent pas directement à calculer les scores de compatibilité : ceux-ci utilisent les
requêtes et les clés. Inversement, les clés ne sont pas directement moyennées pour fabriquer la sortie ;
ce sont les valeurs qui le sont. Séparer ces rôles donne au réseau davantage de liberté qu’un simple
moyennage des embeddings d’entrée.
Point de vigilance. Les lettres ne désignent pas trois séquences de tokens différentes. Dans cette
auto-attention, les trois projections partent du même tenseur. Pour éviter une ambiguïté, nous
noterons Vatt la matrice des valeurs, et réserverons V à la taille du vocabulaire.

Objectif. Lire le produit QK ⊤ comme une grille de comparaisons, en identifiant précisément ses

À comprendre. Un score est un produit scalaire entre une requête et une clé. La ligne indique la
position qui reçoit l’information ; la colonne indique la position susceptible d’en fournir. À ce stade,
le score n’est pas une probabilité.
Pour une tête, chaque requête possède dk coordonnées. Le produit scalaire multiplie les coordonnées
correspondantes puis les additionne. Avec T requêtes et T clés, cette opération remplit une matrice
carrée :
                                     k −1
                                    dX
                            Sij =           qi,r kj,r ,   (T, dk )(dk , T ) −→ (T, T ).
                                    r=0

La transposition de K rend les dimensions internes compatibles. Sans elle, le produit matriciel
demandé n’aurait généralement pas de sens. Le code utilise k.transpose(-2, -1) : seuls les deux
derniers axes sont échangés, pas ceux du lot ou des têtes.
Dans le modèle multi-têtes, Q et K ont la forme (B, H, T, dk ). PyTorch réalise le produit séparément
pour chaque fenêtre et chaque tête. Il obtient (B, H, T, T ) ; les fenêtres d’un lot ne s’échangent donc
aucune information. Les têtes ne sont pas non plus mélangées lors de ce produit.
Prenons qi = (2, −1) et deux clés (1, 3) et (−2, 0). Les scores valent respectivement 2 − 3 = −1 et
−4 + 0 = −4. Le premier score est plus grand, bien qu’il soit négatif. Le softmax dépendra de leur
différence ; le signe négatif n’interdit pas qu’une position reçoive un poids important.
Avec un cache de longueur p, seules les nouvelles requêtes sont calculées pour cet appel, tandis
que les clés anciennes sont concaténées aux nouvelles. La grille devient rectangulaire, de forme
(B, H, T, p + T ). Ce changement de forme explique pourquoi un simple triangle carré n’est plus
toujours le bon masque.
Point de vigilance. Le calcul construit toutes les comparaisons avant de masquer le futur dans le
chemin manuel. Le masque ne supprime donc pas ce coût de construction. Sans cache, la grille de
scores contient BHT 2 nombres, une croissance quadratique en longueur.

Objectif. Suivre les opérations view et transpose sans confondre découpage des coordonnées et
découpage de la séquence.
À comprendre. Les têtes traitent les mêmes positions, mais utilisent des groupes différents de
coordonnées projetées. Chaque tête calcule sa propre grille de scores et ses propres mélanges de
valeurs.
MiniGPT exige que D soit divisible par H. La dimension d’une tête vaut dk = D/H. Chaque
projection produit d’abord (B, T, D), puis le code réorganise les deux derniers axes :

                                    view                   transpose(1,2)
                        (B, T, D) −−−→ (B, T, H, dk ) −−−−−−−−−→ (B, H, T, dk ).

Ces opérations ne créent pas de nouveaux paramètres et ne calculent pas de moyennes. Elles changent
la manière d’interpréter et de parcourir les coordonnées déjà présentes. La transposition met l’axe
des têtes avant celui des positions pour que les produits matriciels utilisent les deux derniers axes.
Prenons un token dont le vecteur projeté est (0, 1, 2, 3, 4, 5, 6, 7) avec D = 8 et H = 4. Les quatre
têtes reçoivent respectivement (0, 1), (2, 3), (4, 5) et (6, 7). Chacune reçoit ce découpage pour tous
les tokens, pas seulement pour un quart de la fenêtre.
Les projections sont apprises avant le découpage. Une coordonnée attribuée à une tête peut donc
dépendre de toutes les coordonnées de l’entrée, grâce à la matrice dense. Il serait trompeur de penser
que la première tête ne voit que les premiers caractères ou seulement les premières coordonnées de
l’embedding initial.
Le nombre de paramètres des trois projections reste 3(D2 + D) quand on change uniquement H. En
revanche, le nombre de grilles de scores augmente avec les têtes, tandis que leur dimension interne
diminue. Des têtes supplémentaires ne constituent donc pas une multiplication indépendante de
toute la largeur du modèle.
Point de vigilance. Les paramètres positifs doivent être des entiers véritables : le constructeur
rejette notamment les booléens. En mode RoPE, une contrainte supplémentaire impose que dk soit
pair, car les coordonnées seront utilisées par paires.

FeedForward

Objectif. Comprendre le calcul effectué à chaque position après l’attention et donner une première
lecture probabiliste de GELU.
À comprendre. Le réseau feed-forward transforme les coordonnées d’un token sans mélanger
directement les positions. Les mêmes deux couches affines et la même activation sont appliquées à
chaque vecteur de la séquence.
Le premier nn.Linear transforme une largeur D en une largeur F . GELU agit séparément sur
chacune de ces F coordonnées. Le second nn.Linear ramène la largeur à D, puis le dropout est
appliqué. C’est exactement l’ordre du nn.Sequential du dépôt.
                                                                                
                     u = xW1⊤ + b1 ,       FFN(x) = Dropout GELU(u)W2⊤ + b2 .

Pourquoi insérer une activation ? Sans elle, la composition de deux applications affines resterait
affine. Augmenter la dimension intermédiaire ne suffirait pas à créer la non-linéarité attendue. GELU
introduit une réponse qui dépend autrement de la valeur de chaque coordonnée.
Pour la comprendre, imaginons une variable aléatoire Z suivant une loi normale centrée réduite, la
courbe en cloche de moyenne zéro et d’écart-type un. Notons Φ(u) la probabilité que Z soit inférieur
ou égal à u. Alors
                               GELU(u) = uΦ(u),         Φ(0) = 21 .
Le coefficient Φ(u) est compris entre zéro et un : les grandes valeurs positives sont peu atténuées, les
valeurs très négatives le sont beaucoup. Cette lecture ne signifie pas que GELU tire une variable
aléatoire à chaque appel ; l’activation elle-même est déterministe.
Par symétrie de la loi normale, Φ(−u) = 1 − Φ(u). On en déduit notamment que GELU peut produire
des valeurs négatives, contrairement à une activation qui remplacerait toutes les entrées négatives
par zéro. Elle ne transforme pas non plus le vecteur complet en distribution de probabilités.
Point de vigilance. Le dropout de ce FFN se trouve après la deuxième couche linéaire, et non
entre les deux couches. Les exemples classiques d’autres bibliothèques ne remplacent pas la lecture
de cette séquence précise.
Exercice. Pour D = 16 et F = 32, comptez les paramètres du FFN, biais compris. Puis, en posant
Φ(1) = p, exprimez GELU en un et en moins un.
Correction détaillée. La première couche possède 16 × 32 + 32 = 544 paramètres ; la seconde
32 × 16 + 16 = 528, soit 1072 au total. GELU et le dropout n’ajoutent aucun paramètre. Les
activations demandées valent p et −(1 − p). Leur différence vaut exactement un, sans qu’il soit
nécessaire de connaître une approximation décimale de p.

Objectif. Comprendre ce que change l’addition d’une entrée à sa transformation, puis distinguer
cet avantage de ses limites dans un bloc post-normalisé.
À comprendre. Une connexion résiduelle additionne deux tenseurs de même forme. Elle permet
à une sous-couche d’apprendre une modification de la représentation plutôt qu’un remplacement
complet de celle-ci.
Le bloc calcule d’abord x + attn_output, puis, après normalisation, x + ffn_output. Les sorties
d’attention et de FFN ont donc nécessairement la même largeur D que le chemin qui les contourne.
Aucune concaténation n’a lieu : la largeur reste inchangée.
Pour saisir le rôle de l’addition dans la rétropropagation, prenons un cas scalaire sans normalisation.
Si f est une fonction dérivable et si ℓ mesure une erreur en sortie, alors
                                           dy                  dℓ   dℓ
                                              = 1 + f ′ (x),           1 + f ′ (x) .
                                                                                  
                      y = x + f (x),                              =
                                           dx                  dx   dy
Le terme un vient du chemin direct. Si la dérivée de f est petite, ce chemin peut conserver une
contribution que la seule composition de nombreuses transformations aurait fortement réduite. Pour
des vecteurs, le rôle du nombre un est joué par l’identité.
Un exemple élémentaire suffit : avec f (x) = 0,1x, la transformation seule multiplie localement
les variations par 0,1, tandis que la transformation résiduelle les multiplie par 1,1. Il s’agit d’une
comparaison locale, pas d’une promesse que multiplier de nombreux facteurs 1,1 serait toujours
souhaitable.
Dans MiniGPT, la normalisation intervient après l’addition. Le résultat réel est donc LayerNorm(x +
f (x)). Le gradient traverse aussi cette normalisation ; on ne peut pas considérer que le bloc entier
possède un passage identité totalement intact.
Point de vigilance. Les résidus ne garantissent ni l’absence de gradients nuls ni la stabilité
universelle. Si f ′ (x) = −1 dans l’exemple scalaire, la dérivée de la somme est nulle. Leur utilité tient
à la structure de calcul qu’ils offrent, pas à une impossibilité mathématique d’échouer.
Exercice. Une représentation vaut (1, 2) et la sous-couche produit (3, −1). Quelle somme entre
dans la normalisation ? Si la sous-couche produit plutôt zéro partout, le résultat final du bloc est-il
nécessairement l’entrée ?
Correction détaillée. La somme vaut (4, 1). Avec une sortie de sous-couche nulle, la somme vaut

TransformerBlock

Objectif. Écrire les deux équations du bloc réel et comprendre pourquoi déplacer une normalisation
change l’architecture.
À comprendre. Dans un bloc post-normalisé, chaque normalisation vient après l’addition résiduelle.
MiniGPT suit cet ordre pour l’attention puis pour le réseau feed-forward. Il ne s’agit pas d’un bloc
pré-normalisé.
Notons A le module complet d’attention, comprenant fusion des têtes, dropout de sortie et projection.
Notons F le FFN complet, comprenant son dropout final. Pour l’entrée X, les deux étapes du dépôt
s’écrivent                                                             
                       U = LN1 X + A(X) ,         Y = LN2 U + F(U ) .
Les tenseurs X, U et Y ont tous la forme (B, T, D). La seconde sous-couche reçoit U , déjà normalisé
après l’attention, et non l’entrée originale X. Les deux LayerNorm possèdent leurs propres paramètres.
Un bloc pré-normalisé ferait plutôt apparaître une sous-couche appliquée à une entrée normalisée
avant l’addition. Même si les composants portent les mêmes noms et si les formes restent identiques,
ces compositions ne sont pas interchangeables : en général, normaliser une somme n’est pas additionner
un vecteur à une transformation d’entrée normalisée.
Pour le constater sans calcul compliqué, annulons les deux sorties de sous-couches. Ici, le bloc fournit
alors LN2 (LN1 (X)), généralement différent de X. Un schéma pré-normalisé avec deux branches
nulles conserverait au contraire l’entrée par ses additions résiduelles.
Le code ne place pas de dropout supplémentaire juste après chacune des sommes. Les dropouts sont
déjà à l’intérieur des sous-modules, avec leurs positions propres. Il faut donc éviter de compléter
mentalement ce bloc à partir d’un diagramme de Transformer provenant d’une autre implémentation.
La causalité traverse le bloc : l’attention respecte le masque, puis le FFN et les normalisations
agissent séparément à chaque position. Ces dernières opérations peuvent transformer l’information
disponible, mais n’introduisent pas de lecture des tokens futurs.
Point de vigilance. La présence d’une LayerNorm finale dans MiniGPT ne transforme pas les
blocs en pré-normalisation. Il faut examiner l’emplacement des normalisations à l’intérieur de chaque
bloc pour nommer correctement l’architecture.

MultiHeadSelfAttention._apply_rope

Objectif. Comprendre RoPE à partir des rotations du plan étudiées avec le sinus et le cosinus, sans
recourir aux nombres complexes.
À comprendre. RoPE encode la position en tournant des paires de coordonnées des requêtes et
des clés. Contrairement aux positions apprises, il n’ajoute pas un vecteur positionnel à l’embedding
du token.
Pour une paire (a, b) et un angle θ, la rotation utilisée dans le code donne

                              Rθ (a, b) = (a cos θ − b sin θ, a sin θ + b cos θ).

Les coordonnées d’indices pairs sont extraites dans even, celles d’indices impairs dans odd. La
fonction calcule les deux nouvelles composantes, les empile puis les aplatit pour reconstituer l’ordre
des paires adjacentes. Une tête de dimension quatre contient donc les paires d’indices (0, 1) et (2, 3).
Pourquoi parler de rotation ? Développons la somme des carrés des composantes obtenues. Les termes
croisés se compensent et cos2 θ + sin2 θ = 1, d’où

                            (a cos θ − b sin θ)2 + (a sin θ + b cos θ)2 = a2 + b2 .

La longueur de la paire est conservée en arithmétique exacte. RoPE change son orientation, pas sa
norme. En calcul flottant, on attend cette propriété à l’arrondi près, pas comme une identité bit à
bit pour tous les angles.
Pour θ = 0, le vecteur reste inchangé. Pour θ = π/2, (1, 0) devient (0, 1). Ces angles simples aident à
comprendre la transformation ; le code utilise cependant des angles définis par les positions entières
et les fréquences, pas nécessairement des multiples de π/2.
Dans le test de rotation connue, une tête de dimension deux reçoit la paire (1, 0) avec un décalage
de trois. Sa fréquence vaut un, donc l’angle vaut trois radians. Le résultat attendu est (cos 3, sin 3),
et non une permutation simple.
Point de vigilance. Les valeurs d’attention ne sont pas tournées. Seules les requêtes et les clés
passent dans _apply_rope. La dimension dk doit être paire ; une largeur totale D paire ne suffit pas
si son quotient par le nombre de têtes est impair.
Exercice. Une paire vaut (3, 4). Calculez sa rotation d’angle π/2 et comparez les carrés des normes.
La configuration D = 12, H = 4 convient-elle à RoPE ?
Correction détaillée. La paire devient (−4, 3). Les deux carrés des normes valent 32 + 42 = 25.
La configuration proposée donne dk = 3, impair : elle est refusée pour RoPE, même si douze est
divisible par quatre et conviendrait aux positions apprises.

Fiche 75 — Respecter l’ordre réel de la rétropropagation
/home/runner/work/SHOKOBO/SHOKOBO/mini_gpt/06_train.py

train : zero_grad, backward, step

Objectif. Relier le gradient étudié en mathématiques aux trois opérations qui changent effectivement
les poids. Une itération correcte exige de distinguer le calcul de la perte, l’accumulation des gradients
et la modification des paramètres.
PyTorch construit un graphe de calcul pendant le passage avant. Les tenseurs intermédiaires
permettent de retrouver comment chaque paramètre a contribué à la perte. Appeler loss.backward()
parcourt les dépendances en sens inverse et inscrit les dérivées dans les attributs grad des paramètres.
Cette opération ne constitue pas encore une mise à jour des poids.
À comprendre. Dans la boucle réelle, l’ordre est : passage avant, calcul de la perte,
optimizer.zero_grad(set_to_none=True), loss.backward(), puis optimizer.step(). Le
petit schéma introductif du fichier ne doit pas remplacer la lecture des instructions exécutées.
Effacer les anciens gradients après le passage avant est correct ici : ce passage n’a pas besoin des
attributs grad. En revanche, les effacer entre backward et step priverait l’optimiseur des dérivées
fraîchement calculées. L’option set_to_none=True retire les gradients stockés au lieu de remplir
systématiquement leurs tenseurs de zéros.
Pour comprendre le risque d’accumulation, considérons deux pertes successives :

                      g (1) = ∇θ L1 ,     sans remise à zéro : θ.grad = g (1) + g (2) .

L’accumulation peut être intentionnelle dans d’autres programmes. Ce script, lui, veut une mise à
jour par lot et remet donc les gradients à zéro à chaque itération. Il ne réalise pas une accumulation
contrôlée sur plusieurs micro-lots.
La valeur affichée par loss.item() correspond au calcul effectué avant la mise à jour. Elle devient
un nombre Python pour les statistiques ; ce nombre ne conserve pas le graphe nécessaire à la
rétropropagation. On ne remplace donc jamais loss.backward() par un appel sur cette valeur
détachée.
Exercice. Pour une illustration en descente simple, prendre L(θ) = (θ − 3)2 , θ = 1 et η = 0,1.
Calculer une mise à jour, puis expliquer les effets d’une remise à zéro effectuée au mauvais endroit.
Correction détaillée. La dérivée vaut 2(θ − 3) = −4. Une descente simple donnerait θ′ =
1 − 0,1(−4) = 1,4, donc un déplacement vers trois. Effacer le gradient juste avant la mise à jour
supprime cette information. Ne jamais l’effacer additionne au contraire des dérivées calculées pour
différents lots et différents poids. Le calcul numérique illustre le principe ; l’optimiseur réellement
employé est AdamW, dont le déplacement diffère.
Point de vigilance. La construction du graphe dépend de l’enregistrement des gradients, pas
uniquement du mode entraînement. Une perte obtenue entièrement sous no_grad ne peut pas

Objectif. Expliquer pourquoi Adam adapte les déplacements sans prétendre que le script utilise
une simple descente de gradient. Les deux moments se comprennent comme des moyennes pondérées
des dérivées et de leurs carrés.
Dans une descente stochastique élémentaire, un paramètre suit θt+1 = θt − ηgt . Deux coordonnées
ayant des gradients de tailles très différentes reçoivent alors des déplacements très différents. Adam
garde un historique pour lisser les changements et ajuster l’échelle de chaque coordonnée. Les
opérations suivantes se lisent séparément pour chaque nombre du modèle, même si PyTorch les
applique à des tenseurs entiers.
À comprendre. Le premier moment mémorise une direction moyenne. Le second mémorise une
moyenne de carrés, donc une échelle toujours positive. Ce second moment n’est pas directement la
variance : on n’y soustrait pas le carré de la moyenne.

                       mt = β1 mt−1 + (1 − β1 )gt ,           vt = β2 vt−1 + (1 − β2 )gt2 .
Les coefficients compris entre zéro et un donnent davantage de poids au passé lorsqu’ils sont proches
de un. Comme les mémoires commencent à zéro, Adam corrige leur biais initial :
                                    mt                  vt                      mbt
                           m
                           bt =           ,   vbt =           ,   ∆θt = −η √           .
                                  1 − β1t             1 − β2t                  vbt + ε

Le petit ε évite une division par zéro et influence les très petites échelles. Le quotient ne signifie pas
que toutes les coordonnées bougent toujours autant ; il dépend de leurs historiques respectifs.
Le dépôt appelle AdamW, qui reprend ces moments et ajoute une décroissance découplée des poids,
étudiée ensuite. Les valeurs β1 = 0,9 et β2 = 0,999 sont des défauts usuels de PyTorch, non des
arguments écrits dans cet appel. Pour une expérience strictement documentée, consulter aussi la
version installée de la bibliothèque. Les carrés empêchent notamment des gradients positifs et négatifs
de s’annuler dans la mémoire d’échelle, même lorsqu’ils s’annulent partiellement dans la mémoire de
direction.

Correction détaillée. On obtient m1 = 0,2 et v1 = 0,004. Les divisions par 0,1 et 0,001 donnent

m

Point de vigilance. Cet exemple isole les moments : il omet volontairement la décroissance AdamW.
Adapter automatiquement une échelle ne garantit ni convergence globale ni absence de divergence ;
le taux d’apprentissage reste un choix expérimental important et doit être jugé avec la validation.

température, il faut donc distinguer le calcul des probabilités de la règle finale de sélection : une
distribution modifiée peut garder exactement le même maximum.

                                                   (
                                                   −∞ si zi < a,

                                                   zi si zi ≥ a.

conservés ; le quatrième est exclu. Leurs poids (4, 2, 2) donnent les probabilités (1/2, 1/4, 1/4, 0). Pour

Pendant une génération réelle, le premier token ajouté modifie le contexte : la seconde distribution
n’est généralement plus identique.
Point de vigilance. Même k = 1 peut conserver plusieurs tokens si les maxima sont égaux : un
échantillonnage reste alors possible entre eux. Dire « top-k garde exactement k tokens » serait
donc inexact ici. Ce programme n’implémente ni top-p, ni pénalité de répétition, ni recherche par
faisceaux ; ne pas déduire ces méthodes de la présence d’un simple filtre top-k.

Objectif. Suivre les formes du cache KV pendant le préremplissage et la génération incrémentale.
Le cache évite certains recalculs du passé, mais ne contient ni une réponse mémorisée ni tous les
logits précédents.
Au premier appel avec cache, past_key_values vaut None. Le modèle traite le prompt, tronqué à
C tokens si nécessaire. Ce préremplissage calcule les clés et les valeurs à chaque couche. Le retour
possède alors trois éléments : les logits, la perte ici absente, et un tuple contenant une paire de
tenseurs par couche.
À comprendre. Si P positions sont déjà mémorisées, chaque paire a deux tenseurs de forme
[B, H, P, dk ], avec dk = D/H. La mémoire couvre les représentations propres à chacune des L
couches : partager une seule paire entre toutes les couches ne représenterait pas le même modèle.
Tant que P < C, l’appel suivant reçoit seulement le dernier token ajouté. Les nouvelles projections
ont une longueur temporelle de un, puis les clés et valeurs sont concaténées à celles du cache. Les
formes utiles deviennent

                             Q : [B, H, 1, dk ],     K, Vatt : [B, H, P + 1, dk ].

La requête du nouveau token consulte ainsi tout le passé encore conservé. Ses positions commencent
à l’offset P : embeddings appris ou rotations RoPE utilisent ce décalage. Les anciennes clés RoPE,
déjà tournées, ne doivent pas subir une seconde rotation.
Le masque causal compare les positions des requêtes à celles des clés ; il reste correct même lorsque
ces deux longueurs diffèrent. Le modèle vérifie aussi que toutes les couches partagent la même
longueur passée et que la somme passé plus nouvelles positions ne dépasse pas C.
Exercice. Avec B = 1, H = 4, D = 64, L = 2 et un prompt de trois tokens, donner la forme de
chaque tenseur du cache après préremplissage, puis après l’appel incrémental suivant. Combien de
nombres le cache contient-il à chacune de ces étapes ?
Correction détaillée. Chaque tête possède dk = 16 composantes. Les formes sont [1, 4, 3, 16], puis
[1, 4, 4, 16]. Il existe deux tenseurs par couche et deux couches : les totaux sont 2×2×1×4×3×16 = 768,
puis 1024 nombres. Juste après le choix d’un token, celui-ci figure dans idx, mais n’entre dans le
cache qu’au prochain passage du modèle.
Point de vigilance. Le cache est réservé au mode évaluation sans cibles. La fonction de génération
désactive aussi les gradients. Une vérification de formes ne prouve pas qu’un cache provient du
bon prompt : l’appelant doit respecter la continuité de la séquence et ne jamais mélanger deux
historiques.

Objectif. Comprendre le choix exact de fenêtre glissante et ses conséquences sur les positions,

                                               T = min(s, C).

Fiche 90 — Deux usages différents de bfloat16
/home/runner/work/SHOKOBO/SHOKOBO/mini_gpt/06_train.py

train, evaluate ; 07_generate.py : load_model_and_tokenizer

Objectif. Distinguer calcul en précision mixte et conversion des poids. Le même nom d’option
n’entraîne pas exactement les mêmes opérations pendant l’apprentissage et pendant le chargement
pour la génération.
Un nombre float32 occupe quatre octets, contre deux pour bfloat16. Ce dernier conserve une large
plage d’exposants, mais moins de chiffres significatifs. Il peut donc représenter des valeurs de grandes
amplitudes tout en arrondissant plus fortement des nombres proches. Réduire la taille ne signifie ni
conserver toutes les décimales ni réduire automatiquement chaque allocation du programme.
À comprendre. Dans train, le modèle est envoyé vers le périphérique sans conversion explicite de
son type : ses paramètres restent normalement en float32. Le passage avant et le calcul de perte
sont entourés de torch.autocast, activé seulement lorsque la précision demandée est bfloat16.
PyTorch choisit alors les types selon les opérations.
La rétropropagation intervient après ce contexte. Le script ne construit pas de GradScaler et ne
propose pas l’option float16. La validation emploie le même mécanisme d’autocast, en plus du
mode évaluation et de l’absence de gradients. Le passage initial d’affichage des formes, lui, n’est pas
entouré de cet autocast.
À l’inférence, le chargeur crée le modèle, charge les poids, puis appelle model.to(device=device,
dtype=dtype). Ici, choisir bfloat16 convertit réellement les paramètres flottants du modèle. La
fonction generate n’ajoute pas un contexte d’autocast analogue à celui de l’entraînement. Ses
identifiants de tokens restent des entiers.
Autour de un, l’écart entre nombres représentables illustre la différence :

                               ∆bf16 = 2−7 = 0,0078125,       ∆fp32 = 2−23 .

Deux logits très proches peuvent devenir indiscernables après arrondi, ce qui peut affecter un argmax
et, par propagation, toute la suite générée.
Exercice. Un modèle contient exactement un million de paramètres flottants. Estimer leur stockage
en float32 puis après conversion bfloat16. La métrique des octets de paramètres doit-elle forcément
être divisée par deux pendant l’entraînement avec autocast ?
Correction détaillée. Les paramètres seuls occupent quatre millions puis deux millions d’octets.
Pendant l’entraînement décrit, l’autocast ne convertit pas durablement tous les paramètres : leur
compteur d’octets peut rester celui de float32. Il serait donc incorrect d’assimiler automatiquement
précision des calculs et taille des poids stockés.
Point de vigilance. Sur CPU, la disponibilité et la rapidité des opérations réduites dépendent du
matériel et de PyTorch. Commencer par float32, puis comparer explicitement exactitude et durée.
Une précision réduite n’est ni une quantification entière ni une garantie d’accélération sur toute
machine.

La première condition concerne les données ; les autres, l’architecture. Augmenter les époques ne
corrige aucune de ces erreurs.
À comprendre. Une erreur de chargement n’est pas une erreur de génération. Vérifier le chemin du
checkpoint, son format, la configuration et la présence de la dépendance BPE avant de modifier la
température. Un fichier explicitement demandé mais absent, hors chemin par défaut, doit provoquer
une erreur plutôt qu’une substitution silencieuse par des poids aléatoires.
Pour un problème de cache, contrôler le mode évaluation, l’absence de cibles, le nombre de paires
égal à L, leurs formes, leurs périphériques et leurs types. La somme des tokens passés et nouveaux
doit rester dans le contexte. La génération gère le débordement par reconstruction ; un appel direct
doit respecter ces contraintes.
Si la perte devient non finie, vérifier les entrées et le taux d’apprentissage, puis revenir à une
configuration petite en float32. Le code refuse un taux non fini, mais ne garantit pas qu’un taux
fini excessif entraîne de façon stable. Il n’applique pas de clipping pour rattraper automatiquement
une telle situation.
Une génération répétitive peut refléter un petit corpus, peu d’apprentissage ou un choix glouton.
La température change la sélection, pas les connaissances. Le projet n’implémente ni format de
dialogue, ni adaptation aux instructions, ni RLHF, ni récupération documentaire, ni mécanisme de
vérification factuelle.
Exercice. Diagnostiquer trois cas : un prompt vide avec zéro token demandé ; une configuration
RoPE avec D = 60, H = 4 ; une génération qui continue après un point final jusqu’à vingt ajouts.
Lesquels constituent des erreurs ?
Correction détaillée. Le prompt vide est refusé avant la boucle, même pour zéro ajout. La
dimension par tête vaut quinze : elle est impaire, donc RoPE est refusé. La continuation après un
point n’est pas une erreur d’arrêt : aucun EOS ni signe de ponctuation ne déclenche l’arrêt dans ce
programme. La longueur demandée commande seule le nombre d’ajouts.
Point de vigilance. Ne pas attribuer une compréhension fiable à une phrase plausible. Ce modèle
prédit des tokens et peut inventer des affirmations. Ses limites pédagogiques ne sont pas des options
cachées qu’une commande de génération permettrait d’activer.
